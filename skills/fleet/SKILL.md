# Fleet · Codex 适配器

CORE_REF: references/core.md

先读取本 Skill 内的[共同方法](references/core.md)；它只管委派、共享资源和汇合。已在本任务读过且无变更时复用。本文件只补 Codex 的运行差量，不以历史模型名或固定角色档位限制调度。工具名及参数以当前宿主契约为准；下文的 `fork_turns`、`followup_task` 等仅在宿主提供这些接口时适用，不假定所有 Codex 版本都支持它们。

## 先选工作去向，不加调度层

在大量阅读或施工前做一次轻判断：确定性取材交程序；本机短反馈或运行事实密集的工作优先原生 worker；远端材料可达、已有数据授权且能一次性完整交付时，才考虑宿主中另行配置的外部执行渠道。没有实际有净收益的委派、并行或共享写权协调，就由主循环直接推进；不因任务很长而自动加载一层 Fleet 流程。只有材料、能力、权限或返工事实改变才重判。

大量本地材料的整体分析，应在主循环通读前分配取证与分析责任。需要本地提取、筛选时间范围、排除凭据或格式转换时优先用现成程序；只有确需语义归类或证据索引时才调用模型。准备方交回可追溯的原始证据与索引，不只给摘要；主循环只恢复足以划分任务和核验关键判断的事实。

高推理成本主循环保持稀疏：保留任务合同、不可约冲突、跨单元整合、异常裁决、最终采纳和用户交付；批量阅读、常规施工、测试、局部诊断与范围内返修，优先交给能够闭环且综合成本更低的一个执行 owner 或程序。主循环能做不代表应由主循环做，高度耦合的整体工作也不为稀疏而强拆。

外部执行渠道只有在用户已授权、宿主已提供且目标工作流可以独立完成时才使用；Fleet 本身不安装、授权或假设这些渠道存在。返回的是可采用的完整成果时，不再派本机重写一遍，只补关键核验、接线和明确缺口。记录实际渠道、成果及返工；用量缺失就写未知，不伪造合计或降本比例。

## 原生协作

- 使用当前暴露的原生子 Agent 工具；能力、并发和权限以本轮工具契约为准。不要为派子任务新建用户侧 task，也不为 Fleet 启动外部 runner、改全局配置或绕过宿主的委派限制。
- 每次启动先选择模型、推理强度与上下文；采用下方起始映射并根据当前任务调整，不能默认把主模型配置复制给所有 worker。用户明确指定的模型／预算优先，仍须满足可用性和权限。
- 通过本轮工具的真实 `model`、`reasoning_effort` 参数提交选择；若名称或支持档位不同，按工具契约映射，不只在任务消息中写模型名。通常用 `fork_turns="none"` 或适用的部分上下文，给足任务事实、当前约束、来源路径与验收。完整上下文确有必要且选定配置就是当前父配置时，可显式选择继承并记录理由；当前 `fork_turns="all"` 不能同时覆盖模型／推理，不得借它悄悄回到昂贵默认。
- `followup_task` 不提供模型切换参数时，续派会保留原配置。新工作不适配该配置就安全交还写权，用选定参数启动新 Agent；在任务文字里要求换模不算实际切换。选定能力不可用时核对错误，可改用满足需求且成本合理的可用档；不静默回退成最高档或声称已用原选型。
- 原生 worker 可拥有授权内互不冲突的本地文件；派工时明确 ownership，并说明它不是唯一执行者、不得覆盖他人改动。冲突整合、凭据、生产写入、部署、提交和不可逆动作留给主循环；其权限仍来自用户原任务。
- 工具调用按当前说明执行。派出后做互补工作；到真实依赖点再等待。收回或改派可能写共享资源的协作者时，先中断并取得停止证据；只发消息不等于已经停写。
- 当前接口不能调某模型、不能派工或不能取得所需隔离时，说明具体边界并完成仍可直接做的部分，不声称用了不存在的能力。模型身份与费用仅在有实际可观测证据且与交付有关时报告；新上下文不自动等于独立权重或跨模型验证。

## 条件命中后的能力上派

主循环使用较低成本模型时，在开工分配及真实失败后的重规划中识别需要更强能力的完整判断单元。命中以下任一条件，且材料、授权与委派工具都可用时，默认把该单元上派给当前可用的高能力模型，不等用户再次点名：

- 关键架构、跨模块语义或冲突裁决仍有决定性分歧，主循环无法依据现有证据可靠收敛。
- 输入足够、工具正常，但已有尝试暴露出推理或实现能力不足，继续同档重试没有新依据。

任务名称、篇幅、风险标签或笼统的“不放心”不构成上派条件。缺材料先补材料，工具错误先修工具。上派时交出关联难点的完整事实、待决问题、失败证据和验收，不先替高能力模型做完同一调查再让它复述；主循环保留意图、分工、整合与最终责任。实际模型与推理强度必须落实到工具参数，并按当前宿主可用项选择，不默认最高推理档。不能委派时明确阻断和继续路径，不声称已经上派。

## 子任务起始选型

实际进入 Fleet 后按共同方法报告用量：有宿主现成 usage 才报告实际值；没有时一句说明未提供，同时保留模型／强度、工作单元、采纳与返工事实。只有用户明确要求评估或已有自动完整计量时才做完整覆盖表。没有实际委派无需 Fleet 统计。Codex 协议的任务用量事件只有在本宿主确实暴露且能绑定目标运行时才消费；文档存在不等于本会话可读。账户额度不是任务用量，子 Agent 的自然语言自报也不是计量回执。

根据当前宿主实际提供的模型及其可靠性、成本和推理选项选择，不假定某一型号在所有账号中可用。下面是能力档位的起始判断，不是永久模型排名；主模型自己判断，不为每次选择额外调用评估 Agent。

| 工作单元 | 起始候选 |
|---|---|
| 规则完全确定的搬运、计算、转换 | 程序／工具直接执行 |
| 输入清楚、范围窄、错误易发现的提取、查找或小修改 | 已知能胜任的轻量模型，通常低推理强度 |
| 边界明确的一般实现、工具操作、局部排查 | 已知能胜任的均衡模型，通常低或中推理强度 |
| 歧义较多、跨模块推理、复杂诊断或精细专业判断 | 较强推理模型，通常中等，必要时高推理强度 |
| 高度耦合的整体判断、关键架构取舍或较低档难以可靠完成的工作 | 主循环直接做；命中上派条件时，将完整判断单元交给当前可用的高能力模型并单独选择推理强度 |

low/medium 能满足时不选 high；high、xhigh、max、ultra 等较高档需要具体判断深度的理由，尤其不能继承 ultra 当作常规工作设置。高后果但确定性的操作仍靠权限、程序校验与可恢复性保护，不因风险高就把全部工作升到最贵模型。

在派工消息或已有任务记录中留一行“任务性质 → 选定模型／推理／上下文 → 理由”；启动与回收核对实际配置，保留结果、返工和升级事实。几次真实使用后再复盘选型；未知的费用不估作已节省，不为这套规则建后台采集器。
